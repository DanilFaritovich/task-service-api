# Task Service API

[English](README.md) | **Русский**

Асинхронный REST API для управления **задачами, сервисами и пользователями**.

Проект реализован на FastAPI, SQLAlchemy, PostgreSQL, Alembic и Pydantic v2. Он демонстрирует разделение HTTP-обработчиков и бизнес-логики, асинхронную работу с базой данных, миграции и интеграционное тестирование API.

---

## Возможности

- CRUD-операции для задач, пользователей и сервисов.
- Управление привязками сервисов к пользователям, файлами задач и записями логов.
- Получение задач по статусу и поиск пользователя по Telegram ID.
- Получение сводной статистики через эндпоинт дашборда.
- Асинхронные сессии SQLAlchemy и PostgreSQL 16.
- Сервисный слой с вынесенной бизнес-логикой.
- Миграции Alembic и триггеры PostgreSQL для назначения доступных сервисов новым пользователям.
- Валидация данных через Pydantic v2 и централизованная обработка ошибок бизнес-логики и ограничений БД.
- Интеграционные тесты HTTP API с помощью pytest и httpx.

**Статус:** проект предназначен для разработки и локального запуска. JWT-аутентификация, Redis, полноценная конфигурация для production и CI/CD указаны в планах развития и не должны считаться реализованными функциями.

## Архитектура

Проект использует многослойную архитектуру: обработка HTTP, прикладная логика и работа с данными разделены.

```text
     HTTP-клиент
          │
          ▼
   FastAPI Router
  (HTTP и валидация)
          │
          ▼
    Service Layer
  (бизнес-логика)
          │
          ▼
 SQLAlchemy AsyncSession
          │
          ▼
    PostgreSQL 16
```

### Обработка запроса

```text
HTTP-запрос
    │
    ▼
FastAPI Router
    ├── Валидация входных данных
    └── Получение зависимостей
    │
    ▼
Сервисный слой (для прикладных операций)
    ├── Бизнес-правила
    └── Обращения к БД
    │
    ▼
SQLAlchemy AsyncSession
    │
    ▼
PostgreSQL
    │
    ▼
Pydantic-схема ответа
    │
    ▼
HTTP-ответ
```

Базовые CRUD-маршруты для ряда сущностей создаются с помощью `fastcrud`. Для операций, которым нужна дополнительная бизнес-логика, используются отдельные обработчики и сервисы.

### Слои приложения

**API — `backend/api/`.** Содержит FastAPI-приложение, маршруты, зависимости и обработчики ошибок. HTTP-обработчики принимают и валидируют запросы, а затем обращаются к соответствующей логике приложения.

**Сервисы — `backend/api/services/`.** Содержат прикладную логику, например получение задач по статусу, поиск пользователя и статистику дашборда. Сервисы отделены от деталей HTTP.

**База данных — `backend/database/`.** Содержит ORM-модели, Pydantic-схемы, асинхронный движок SQLAlchemy, настройку сессий и определения триггеров PostgreSQL.

**Миграции — `alembic/`.** Alembic управляет схемой базы данных, включая зарегистрированные через `alembic_utils` функции и триггеры.

## Основные технические решения

### Отдельный сервисный слой

Бизнес-логика вынесена из HTTP-обработчиков:

```text
Router → Service → Database
```

Например, `TasksService` проверяет допустимость статуса задачи и выполняет выборку через ORM. Это позволяет отдельно проверять правила приложения и расширять API.

### Асинхронная работа с PostgreSQL

Приложение использует асинхронные сессии SQLAlchemy и драйвер `asyncpg`. Для запросов сессия предоставляется через зависимость FastAPI; параметры подключения и пула считываются из окружения.

### Управление сессией через ContextVar

`ContextVar` хранит ссылку на сессию в контексте выполнения запроса. Сессия также доступна через зависимость `get_db`. Такой подход позволяет компонентам получать контекст текущего запроса, не передавая его вручную через каждый промежуточный вызов.

### Триггеры PostgreSQL

Определения триггеров расположены в `backend/database/triggers/`. В частности, предусмотрена автоматическая привязка доступных сервисов к вновь созданным пользователям.

Эта операция выполняется на уровне базы данных и не зависит от того, создан пользователь через HTTP API или другим способом. Определения функций и триггеров регистрируются в миграциях с помощью `alembic_utils`.

### Обработка ошибок целостности

В приложении предусмотрены HTTP-ответы для типовых ошибок PostgreSQL:

| Ошибка | Ответ API |
| --- | --- |
| Нарушение уникальности | `409 Conflict` |
| Нарушение внешнего ключа | `400 Bad Request` |
| Отсутствие обязательного значения | `400 Bad Request` |
| Нарушение ограничения `CHECK` | `400 Bad Request` |

Ошибки бизнес-логики, например отсутствие пользователя или некорректный статус задачи, также преобразуются в соответствующие HTTP-ответы.

## Быстрый запуск

### Требования

- Docker с поддержкой Docker Compose.
- Python 3.14 и `pip` для локального запуска API.
- Свободные порты `5432` для PostgreSQL и `8000` для API.

**Важно:** текущий `docker-compose.yml` запускает **только PostgreSQL**. Само приложение FastAPI запускается отдельно на компьютере через Python.

### 1. Клонирование репозитория

```bash
git clone https://github.com/DanilFaritovich/task-service-api.git
cd task-service-api
```

### 2. Настройка окружения

```bash
cp .env.example .env
```

Если PostgreSQL запускается через приведённый Docker Compose, а API — локально на том же компьютере, укажи в `.env`:

```dotenv
DB_HOST=localhost
DB_PORT=5432
DB_USER=app_user
DB_PASSWORD=app_password
DB_NAME=app_db
```

Остальные параметры можно оставить из `.env.example`. В исходном примере `DB_HOST` задан как `172.17.0.1`: этот адрес не универсален, поэтому для описанного локального запуска используется `localhost`.

Учётные данные в `docker-compose.yml` предназначены для демонстрационного окружения. Для работы с реальными данными установи собственные значения и не публикуй файл `.env`.

### 3. Запуск PostgreSQL

```bash
docker compose up -d
```

Чтобы проверить состояние контейнера:

```bash
docker compose ps
```

### 4. Установка зависимостей

```bash
python3.14 -m venv .venv
source .venv/bin/activate
python -m pip install -r requirements.txt
```

В Windows команда активации виртуального окружения отличается.

### 5. Применение миграций

```bash
alembic upgrade head
```

Эта команда создаёт или обновляет объекты базы данных в соответствии с миграциями проекта.

### 6. Запуск API

```bash
python main.py
```

После запуска приложение доступно по адресу:

```text
http://localhost:8000
```

Точка входа `main.py` запускает Uvicorn в режиме автоматической перезагрузки, удобном для локальной разработки.

## API и документация

FastAPI предоставляет интерактивную документацию на основе OpenAPI:

- **Swagger UI:** http://localhost:8000/docs
- **ReDoc:** http://localhost:8000/redoc
- **Проверка сервиса и подключения к БД:** http://localhost:8000/health

### Основные группы эндпоинтов

| Путь | Назначение |
| --- | --- |
| `/tasks` | CRUD-операции с задачами |
| `/tasks/status/{status}` | Получение задач с указанным статусом |
| `/users` | CRUD-операции с пользователями |
| `/users/tg/{tg_id}` | Получение пользователя по Telegram ID |
| `/services` | CRUD-операции с сервисами |
| `/user-services` | Привязки сервисов к пользователям |
| `/task-files` | Метаданные файлов задач |
| `/logs` | Работа с записями логов (без обновления и удаления через CRUD) |
| `/dashboard/stats` | Сводная статистика |

Допустимые статусы задачи: `pending`, `running`, `completed`, `failed`, `cancelled`.

Точные HTTP-методы и схемы запросов для CRUD-эндпоинтов можно посмотреть в `/docs` после запуска приложения.

## Тестирование

**Внимание:** тесты используют базу данных, указанную в конфигурации, и перед тестами очищают таблицы `task_files`, `logs`, `tasks`, `user_services`, `services` и `users` через `TRUNCATE ... CASCADE`. Не запускай тесты на базе с данными, которые необходимо сохранить. Используй отдельное тестовое окружение или отдельную тестовую БД.

Для запуска тестов нужны работающий PostgreSQL и установленные зависимости из `requirements.txt`.

Полный набор тестов:

```bash
pytest tests/ -v
```

Отдельный модуль:

```bash
pytest tests/test_tasks.py -v
```

Тесты используют `pytest`, `pytest-asyncio` и `httpx`. HTTP-запросы отправляются к ASGI-приложению, а результаты проверяются в том числе через реальную тестовую базу PostgreSQL.

В исходном README также приведена команда `pytest --cov=backend tests/`. Для неё потребуется дополнительно установить плагин `pytest-cov` — в текущем `requirements.txt` он не указан.

## Миграции базы данных

Создание миграции на основе изменений ORM-моделей:

```bash
alembic revision --autogenerate -m "description"
```

Применение миграций:

```bash
alembic upgrade head
```

Откат последней миграции:

```bash
alembic downgrade -1
```

Просмотр текущей ревизии:

```bash
alembic current
```

Перед применением автоматически созданной миграции проверь её содержимое, в том числе изменения функций и триггеров PostgreSQL.
